# Site Favicons Implementation Plan

> **For agentic workers:** Use executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Wherever the dashboard marks a site with its initial on a tinted tile, it shows the site's own favicon: the server finds the icon's URL in the site's HTML once and stores it, the browser loads the image from wherever that HTML points (the site, or its CDN), and the initial stays as the fallback.

**Tech Stack:** let-go 1.13 (`http/request`, `async` go blocks) / DuckDB / ragtime migrations on the server; React 19 / TypeScript / Tailwind 4 in `ui/`; Playwright 1.56 in `e2e/`.

**Repo:** `~/Projects/pagelet`. Work on a branch `site-favicons` off `master` and open a PR, as the earlier work did. Run every command through mise (`mise exec -- lgx ...`, `mise exec -- npx ...`).

## Design

### The problem

`ui/src/components/SiteMark.tsx` draws each site as its first letter on a soft tile tinted by a hash of the domain. It stands in three places: the overview's cards (`Sites.tsx`, large), the site switcher's button and menu (`SiteSwitcher.tsx`, small), and the plain label a public-dashboard visitor sees (`TopBar.tsx`, small). The owner wants the site's favicon there, as every analytics dashboard has.

The component's comment records why there were none: "fetching them would tell a third party which sites are watched." That rules out icon services (Google's `s2/favicons`, DuckDuckGo's `icons.duckduckgo.com`), and it still does. It does not rule out asking the site itself.

### The shape: the server stores a link, the browser loads the image

Three designs were weighed. (1) The browser loads `https://<domain>/favicon.ico` and nothing else changes: smallest, but misses every site whose icon is declared only by a `<link rel="icon">` tag. (3) The server fetches the icon bytes, stores them in DuckDB and serves them from its own route: the only design in which a viewer's browser never contacts the tracked site, and the pattern of Plausible and Bitwarden, but the most work (binary storage, a proxy route, cache headers, a refresh policy). This plan is (2), the middle: **the server reads the site's HTML once, stores the icon's URL, and the browser loads the image from the site**, with `/favicon.ico` and then the initial as fallbacks. It closes the coverage gap of (1) with a string column and a small module, and does not take on (3)'s bytes.

What (2) does not do: a viewer's browser still loads the image from a host the dashboard does not control. That host is whatever the site's own HTML names: usually the site itself, sometimes its CDN (`cdn.example.net`), chosen by the site's owner and not by pagelet. The owner owns that site, and a visitor to a public dashboard reveals their address to a host the site's owner already chose to serve its visitors from. `referrerPolicy="no-referrer"` on the image keeps the dashboard's URL out of that host's logs. The claim to make in the docs is "never an icon service picked by pagelet", not "never anyone but the site". If this ever matters, (3) can replace the `src` without changing how the mark is used.

### Caching, honestly

Nothing on pagelet's side can set cache rules for an image another host serves: the site's response headers decide. In practice this is fine. Favicons are static files, and sites serve them with a `Cache-Control` max-age (a hashed asset like `/assets/favicon-a1b2c3.png` usually comes with a year-long `immutable`); a response with only a `Last-Modified` gets heuristic freshness, about a tenth of its age. Within one loaded dashboard the browser also reuses an image it already has for the same URL when a second `<img>` for it mounts (the switcher opening again), so the per-mount "requests" are memory or disk cache hits after the first. A site that forbids caching outright is re-fetched on each mount; that is the site's choice, and it affects that site only.

### The server side

**Column.** Migration `009-add-sites-icon-url`: `alter table sites add column icon_url varchar`; down drops it. No constraint (DuckDB takes none in `add column`). Null means "not resolved yet": existing sites after the upgrade, a site in the moments after it is created, and a site whose settings were just saved. `site-columns` in `db.lg` adds `icon_url`, so every site JSON carries `icon_url: string | null`.

- `db/update-site!` sets `icon_url` to null on every save, domain changed or not. Every save re-resolves (below), and null is the one signal the dashboard reads for "still looking", so a save that keeps the domain must show as pending too, or a moved icon would never reach a mounted dashboard. The cost is a mark that, for a few seconds after a save, tries `/favicon.ico` on its own, which for most sites is the same picture. Settings saves are rare.
- `db/set-icon-url!` (`[conn id domain url]`) writes `update sites set icon_url = ? where id = ? and domain = ?`: the result is stored only for the domain it was resolved for. Two fetches can overlap (the startup pass and a save, or two quick saves), and the older can finish last; with the domain in the `where`, a result for a domain the site no longer has touches no row. Two results for the same domain can still land in either order (one may have failed, or the page changed between them); whichever finishes last stands, and the next save re-resolves. Accepted: a decoration, repaired by a save.
- `db/sites-without-icon` (`[conn]`): the sites whose `icon_url` is null, in position order.

**Module `src/pagelet/favicon.lg`.** Pure functions, then the fetch, then an integrant component.

- `(default-icon-url domain)` is `https://<domain>/favicon.ico`.
- `(icon-href html)`: the `href` of the best `<link>` in the first 64 KB of `html`, or nil. It scans `<link ...>` tags with a regex, reads each tag's attributes with a second regex that takes any attribute order and double, single or no quotes, and splits `rel` on whitespace, case-insensitively. Preference: a `rel` containing `icon` but not `apple-touch-icon` or `mask-icon` first (`icon`, `shortcut icon`); otherwise `apple-touch-icon`; `mask-icon` never (it is a monochrome Safari pinned-tab shape). Among equals, the first in the document.
- `(resolve-href domain href)`: an absolute `http://` or `https://` URL is kept; `//host/path` gets `https:`; `/path` and `path` are joined under `https://<domain>/`; anything else (`data:`, `javascript:`, blank) is nil. The page's final URL after redirects is not known (let-go's response carries status, body and headers only), so a relative href is resolved against the domain as entered; most sites serve their assets on both the apex and `www`, and a miss falls through to `/favicon.ico` in the browser.
- `(fetch-icon-url fetch domain)`: calls `(fetch (str "https://" domain "/"))` and returns the resolved href from a 2xx body, or the default. `fetch` is a function of a URL to a response map (`{:status :body :headers}`) that may throw; any throw, non-2xx, missing tag or unresolvable href yields the default. The default is stored, not null, so a site that cannot be read is not asked again on every start.
- `http-fetch`, the real `fetch`: `http/request` (not `http/get`, which takes no timeouts) with `:timeout {:connect 3 :request 5}`, `User-Agent: Pagelet (+https://github.com/abogoyavlensky/pagelet)` and `Accept: text/html`. Go's client follows up to ten redirects. The whole body is read (let-go has no size limit short of streaming); the 5 s request timeout bounds it, and `icon-href` looks at the first 64 KB only.
- Component `:pagelet.favicon/resolver`, config `{:db conn :fetch fn}` (`:fetch` optional, `http-fetch` by default; tests pass a stub). `init-key` returns `{:db :fetch}` and starts one `go` block that resolves every site from `db/sites-without-icon`, one after another, so a server upgraded with sites gets their icons without anyone asking. `halt-key!` does nothing: a go block still running at shutdown prints a failure when the connection is gone, and that is all.
- `(refresh! resolver site)`: in a `go` block, `fetch-icon-url` for the site's domain, then `db/set-icon-url!` with that domain; a throw is printed as `pagelet: favicon for <domain> failed: <message>` and the default stored. Returns a channel that receives the URL it tried to store, so a test can wait on it (`async/alts!!` with a timeout) instead of polling the table.

Why a go block: the request path must stay quick and never wait on another host. The ingest flusher already runs in one (`ingest.lg`, `start-loop!`), with blocking takes inside, so a blocking HTTP call there is in keeping.

**Routes.** `routes.lg` takes `:favicons` in its deps. `POST /api/sites` calls `(favicon/refresh! favicons site)` after `ingest/refresh-sites!`, and so does `PUT /api/sites/:id`, whether or not the domain changed: saving Settings is the owner's way to re-read an icon that moved, with no button to add. The handler does not wait for the result; the 201 or 200 carries `icon_url` as it is at that moment (null for a new site). The `routes_test` fixture adds a `:favicons` built with a stub `fetch`.

**System.** `system.lg` adds `:pagelet.favicon/resolver {:db (ig/ref :pagelet.db/conn)}` and gives the handler `:favicons (ig/ref :pagelet.favicon/resolver)`.

**An outbound request from the server.** It is admin-triggered only, to `https://<domain>/` where `domain` has already passed `routes.lg`'s hostname check (no scheme, path or port), with short timeouts. A redirect could send it anywhere, including a loopback address; a GET with no cookies or body is the whole exposure. docs/KNOWLEDGE.md gets a note; the backlog gets nothing, since there is nothing deferred.

### The dashboard

`Site` in `ui/src/api.ts` gains `icon_url: string | null`.

**Learning the result.** The resolver answers after the request that started it, and the pages load the site list once (`useApi` in `Sites.tsx` and `Site.tsx`; the 60 s refresh reloads reports only). So a `null` in a loaded list means "the server is still looking". A small hook, `useIconResolution(sites, refresh, enabled)` in `ui/src/api.ts` beside `useApi`, re-asks for the list 6 s after it sees a loaded site with `icon_url` null (past the fetch's 5 s request timeout) while `enabled` holds; the effect runs again on the new list, so it keeps asking every 6 s while a null remains, up to ten times per mount of the page (a minute: the startup pass after an upgrade resolves sites one after another, up to 5 s each, and a public dashboard opened in that minute should still catch its icon). The counter lives in a `useRef` and so resets with the page, which is where a navigation lands. It calls the quiet `refresh` (no loading state), as the 60 s refresh does. Both pages call it with their `sites` state. The overview passes `!busy` as `enabled`, the same guard it gives `useRefresh`: no list request may land under a drag or on top of an unsaved order, and `useApi`'s generation counter already drops an in-flight answer when the overview mutates the list on drag start. The site page passes `true`. Since a save nulls `icon_url`, the save's own reload of the list (`onSaved`) brings the null in and starts the hook's timer; nothing else is needed for a save that keeps the domain. Meanwhile the mark for a pending site tries `https://<domain>/favicon.ico` itself, so most sites show their icon before the server has answered, and the reload only matters for the sites whose icon is somewhere else. A visitor's view of a public site loads one site the same way through `api.site`; the hook takes a list, so the page wraps that one site in an array.

`SiteMark` takes `{ site, size }` instead of `{ domain, size }`; its three call sites pass the `Site`. It builds the candidate list `[site.icon_url, default]` with the default (`https://<domain>/favicon.ico`) dropped when it equals `icon_url`, and nulls removed. It tries them in order: an `<img>` for the current candidate, hidden until `onLoad`; `onError` moves to the next; past the last, the initial tile stays. The image carries `alt=""`, `referrerPolicy="no-referrer"` and `data-testid="site-icon"`; the tile keeps `aria-hidden` and gets `data-testid="site-initial"`.

A module-level `Set<string>` of URLs that failed in this page's lifetime skips them on later mounts (the switcher mounts a mark per site each time it opens, and browsers do not cache a 404 for long). Marks mounting at the same moment, before the first answer, may still each ask once. The set is never cleared short of a page reload: an icon that comes back to life at the same URL shows after the next reload, which is fine for a decoration.

The state belongs to one site and one `icon_url`: Settings can change the domain, and the resolver changes `icon_url` under a mounted mark. The exported `SiteMark` is a thin wrapper rendering the stateful mark with `key={`${site.domain} ${site.icon_url}`}`, so either change remounts it fresh. Call sites do not change for this.

Markup:

- **Small (`sm`, 20 px):** the loaded image replaces the tile outright: `size-5 rounded-md object-contain`, no background. An icon beside its domain, as a switcher reads best.
- **Large (`lg`, 40 px):** the tile stays as a neutral frame, `size-10 rounded-xl bg-track` (not the domain tint, which would fight the icon's colours), with the image `size-6 object-contain` centred. A 32 px favicon is not scaled past itself.

The component's docstring is rewritten: the mark is the site's favicon, from the site itself and never a service, with the server-found URL first and `/favicon.ico` and the initial as fallbacks.

### Testing

- `test/pagelet/favicon_test.lg`: `icon-href` on tags with `rel="icon"`, `rel="shortcut icon"`, `REL='Icon'`, attributes in either order, unquoted values, an `apple-touch-icon` alone, a `mask-icon` alone (nil), an `apple-touch-icon` before an `icon` (the `icon` wins), and no tag; `resolve-href` for each of the five shapes and `data:`; `fetch-icon-url` with a stub `fetch` for a 2xx body with a tag, a 2xx without, a 404, and a throw.
- `test/pagelet/db_test.lg`: `set-icon-url!` with the site's domain writes; with another domain it writes nothing; `update-site!` nulls `icon_url`, domain changed or not.
- `test/pagelet/favicon_test.lg` also covers the component: a site inserted with a null `icon_url`, then `ig/init` of the resolver with a stub `fetch`, and the row is filled within 2 s (poll). And the stale case: a stub whose first answer blocks on a channel; `refresh!` for domain A, rename the site to B, `refresh!` for B, let A's answer through; the row holds B's URL.
- `test/pagelet/routes_test.lg`: a created site's JSON has `icon_url` null; after the resolver's answer (`GET /api/sites/:id` polled for up to 2 s) it shows the stub's URL; a `PUT` with the stub changed yields the new one; every `PUT` answers with `icon_url` null. `db_test`'s migrate-and-roll-back accommodates migration 009.
- `e2e/tests/favicon.spec.js`, after `tracker.spec.js`'s way of routing a made-up host. Two sites on unique `.test` domains, created through the API; the server's own fetch of `https://<domain>/` fails (no such host), so both get the default URL. For the first, `page.route` fulfils `https://<domain>/favicon.ico` with `ui/public/icon-192.png` as `image/png`; for the second, the route answers 404. On the overview, the first card has a `site-icon` with `naturalWidth` above 0 and no `site-initial`; the second has the initial and no icon. Open the first site: the switcher button shows the icon. Open the switcher menu, close, open again: the second site's row shows the initial each time and the page made one request in all for that URL (count with `page.on('request')` from before the first `goto`). Rename the second site's domain in Settings to a third unique domain whose `/favicon.ico` is routed to the PNG: the switcher's mark becomes the icon without a reload (the save reloads the list, the renamed site is pending, and its mark tries the new domain's `/favicon.ico`). Then, on the first site, change the routed `/favicon.ico` to a 404 and save its Settings unchanged: within about 10 s the mark falls back to the initial without a reload (the save nulls the URL, the hook re-asks, the remounted mark finds the icon gone). This covers the same-domain save. Delete all sites at the end. The `<link>` path is not reachable from e2e (no DNS for `.test` hosts); the unit tests own it.

### Out of scope

Serving the icon bytes from pagelet (design 3); a "refresh icon" control (saving Settings does it); an owner-uploaded icon; retrying a site whose fetch failed (it gets the default until its Settings are next saved).
