# pagelet v1 Implementation Plan

> **For agentic workers:** Use executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A single-binary, self-hosted, cookie-less web analytics service: a let-go server over DuckDB that ingests page views from a tiny tracker script and serves a React dashboard for several sites.

## Design

### What v1 is

One binary, one DuckDB file. A site owner puts `<script defer src="https://analytics.example.com/p.js"></script>` on any number of sites, adds each site's domain in the dashboard, and sees visitors, pageviews, a timeseries, top pages, referrers, browsers, OS, devices, custom events, and who is online now. No cookies on tracked sites. One admin password for the dashboard. Reports are in UTC.

### Non-goals for v1

Geo (country from IP), bounce rate, time on page, local-timezone reporting, data retention or rollups, Parquet export, accounts or sign-up, gzip, deployment (compose.yaml and deploy.yml are the next plan, once a remote and a server exist).

### Architecture

Shaped like quickmeet: an integrant system configured from environment variables with development defaults, ruuter routes behind one Ring-style handler, ragtime migrations, `resources/` embedded into the binary by `lgx build`. Differences from quickmeet: DuckDB instead of sqlite, no HoneySQL (plain SQL strings), an in-memory ingest buffer with a flush loop, signal-driven shutdown, and a Vite-built React dashboard in `ui/` whose output ships inside the binary.

Components, in integrant start order: `::db/conn` → `::ingest/buffer` → `::routes/handler` → `::server/http`. Halt runs in reverse, so the server stops taking requests, then the buffer does its final flush, then the database closes.

### Data model (DuckDB)

```sql
create table sites (
  id varchar primary key,          -- 12 hex chars
  name varchar not null,
  domain varchar not null unique,  -- lower-cased hostname, no port
  created_at timestamp not null);

create table events (
  site_id varchar not null,
  ts timestamp not null,           -- naive UTC
  name varchar not null,           -- 'pageview' or a custom event name
  visitor varchar not null,        -- daily hash, 64 hex chars
  path varchar not null,
  referrer varchar,                -- referrer host, null when none or internal
  browser varchar, os varchar, device varchar,
  props varchar);                  -- JSON text or null

create table sessions (            -- dashboard logins
  id varchar primary key, created_at timestamp not null);

create table salts (               -- one row per UTC day
  day date primary key, salt varchar not null);
```

`props` is `varchar` holding JSON text. Task 2 checks whether the driver build has DuckDB's `json` extension (`select '{"a":1}'::json`); if it does, use `json` for the column, otherwise keep `varchar`. Nothing in v1 queries inside props.

Timestamps: every insert uses `now() at time zone 'UTC'`, which yields a naive UTC `timestamp` regardless of the pool connection's session timezone. Period boundaries in queries are ISO strings cast with `?::timestamp`. Day-of-event comes from the SQL `ts::date`; the daily salt's day comes from `(now() at time zone 'UTC')::date`. No date code in let-go.

### Ingest

`POST /api/event`, body `text/plain` (so browsers send no CORS preflight) containing JSON:

```json
{"d": "example.com", "u": "https://example.com/pricing?utm_source=x", "r": "https://news.ycombinator.com/", "n": "pageview", "p": {"plan": "pro"}}
```

The handler does the minimum and never binds dynamic vars (let-go 1.13.0 runs every handler on one shared binding stack; see `~/Projects/quickmeet/docs/backlog/letgo-http-handlers-share-dynamic-bindings.md`):

1. Parse JSON. Reject a body over 4 KB, a missing `d`/`u`, or an `n` that is not 1-64 chars of `[a-zA-Z0-9_-]`.
2. Look up the site by `d` (lower-cased) in the sites atom (a map of domain to site, refreshed whenever the sites table changes). Unknown domain: answer 202 and drop, so the endpoint reveals nothing.
3. Parse the user agent with the `useragent` library. `Bot` true: 202 and drop.
4. Client IP: with `TRUST_PROXY=true`, the first comma-separated entry of `x-forwarded-for`; otherwise `:remote-addr` with the port stripped (handle `[::1]:port`).
5. Path: the URL's path only (drop query and fragment), `/` when empty, with `h` (the tracker's hash-route fragment, sent only in hash mode) appended when present, so `/#/about` is stored as `/#/about`. Referrer: the host of `r`, `www.` stripped, `nil` when blank or equal to the site's domain.
6. Props: when `p` is a map, `(json/write-json p)`; if that is longer than 2048 characters, props becomes `nil` (never truncated: a cut JSON string would be invalid and could fail a whole batch).
7. `swap!` a map `{:site-id :name :ip :ua :path :referrer :browser :os :device :props}` onto the buffer atom (a vector). Answer `202` with an empty body and `Access-Control-Allow-Origin: *`.

The visitor hash is **not** computed in the handler. The buffered row carries the IP and user agent for at most one flush interval, in memory only, and the flusher hashes it right after it has ensured today's salt. That way the hash and the row's `ts` are stamped in the same step and cannot straddle midnight differently. Neither the IP nor the user agent is ever written to DuckDB.

The **flush loop** is a `go-loop` started by `::ingest/buffer` on init, using `async/alts!!` over `(async/timeout interval-ms)`, a `kick` channel (the handler puts on it when the buffer reaches 500 rows) and a stop channel. Init also loads the sites cache and ensures today's salt before the component returns, so a restarted server accepts events for existing sites from its first request. On every tick, inside one `try` that logs any exception and continues:

1. Ensure the salt: `select day::varchar as day, salt from salts where day = (now() at time zone 'UTC')::date`. If none, insert a fresh `(random-hex)` for today, delete rows older than today, and reset the salt atom to `{:day .. :salt ..}`. If this step throws, skip the flush for this tick (the rows stay buffered) rather than hashing with a stale salt.
2. `swap-vals!` the buffer to `[]` and take the old vector. Drop rows whose `:site-id` is no longer in the sites cache (a site deleted while they were queued). Hash each remaining row: `visitor = (hash/sha256 (str salt "|" site-id "|" ip "|" ua))`, then dissoc `:ip` and `:ua`. Insert in 200-row batches with one `insert into events values (?, now() at time zone 'UTC', ?, ?, ?, ?, ?, ?, ?, ?), ...` statement per batch.

A failed batch is logged and its rows are dropped (analytics, not bookkeeping). `halt-key!` closes the stop channel and takes from a `done` channel; the loop puts on `done` in a `finally` so shutdown can never hang, and runs one last flush before it does.

Concurrency: `swap!` is mutex-backed in let-go (`pkg/vm/atom.go`), and the flush loop is the only writer to `events`, so DuckDB's MVCC never sees write contention. Dashboard reads run on other pool connections concurrently.

### Shutdown

`main.lg` starts the system, then blocks on a channel. `syscall/signal-notify` (Linux only in let-go 1.13.0; `pkg/rt/syscall_linux.go:599`) delivers `SIGINT`/`SIGTERM` onto it. On a signal, `ig/halt!` runs, then the process exits 0. On platforms where `signal-notify` throws "unsupported" (macOS), catch it and fall back to `http/wait`, as quickmeet does.

### Dashboard API

All `/api/*` routes except `/api/health`, `/api/event` and `/api/login` require a valid session cookie; otherwise 401 `{"error":"unauthorized"}`.

| Route | Does |
|---|---|
| `GET /api/health` | `{"ok":true}`, public; the Docker smoke test and uptime checks use it |
| `POST /api/event` | ingest (above) |
| `POST /api/login` `{"password"}` | compare `(hash/sha256 password)` with the hash of `ADMIN_PASSWORD`; on match insert a session and set the cookie; 401 otherwise |
| `POST /api/logout` | delete the session, clear the cookie |
| `GET /api/me` | `{"ok":true}` when signed in (the UI's session probe) |
| `GET /api/sites` | `[{id,name,domain,created_at}]` ordered by name |
| `POST /api/sites` `{"name","domain"}` | validate (domain: lower-cased hostname, `[a-z0-9.-]+`, 1-253 chars, no scheme or port; name 1-64 chars); 409 on duplicate domain; refresh the sites atom |
| `PUT /api/sites/:id` `{"name","domain"}` | same validation; 404 unknown id |
| `DELETE /api/sites/:id` | refresh the sites atom without the site first (so the flusher discards anything still queued for it), then delete the site and its events in one transaction |
| `GET /api/sites/:id/stats?period=today\|7d\|30d\|custom&from=YYYY-MM-DD&to=YYYY-MM-DD` | every panel in one JSON (below) |
| `GET /api/sites/:id/realtime` | `{"online": n}`: `count(distinct visitor)` in the last 5 minutes |
| `GET /p.js` | the tracker, `text/javascript`, `Cache-Control: public, max-age=86400` |
| `GET /app/:file` | Vite output from `resources/public/app/` |
| `GET /`, `GET /login`, `GET /sites`, `GET /sites/:id` | the app's `index.html` (SPA fallback for the routes the UI has) |

Stats response shape (the UI and `stats.lg` must agree on it exactly):

```json
{"period": {"from": "2026-09-23T00:00:00", "to": "2026-09-30T13:00:00", "bucket": "day"},
 "totals": {"visitors": 120, "pageviews": 340, "views_per_visitor": 2.8},
 "timeseries": [{"t": "2026-09-23", "visitors": 10, "pageviews": 25}],
 "pages":     [{"name": "/pricing", "visitors": 40, "pageviews": 60}],
 "referrers": [{"name": "news.ycombinator.com", "visitors": 30, "pageviews": 35}],
 "browsers":  [{"name": "Chrome", "visitors": 80, "pageviews": 200}],
 "os":        [{"name": "macOS", "visitors": 50, "pageviews": 120}],
 "devices":   [{"name": "desktop", "visitors": 90, "pageviews": 250}],
 "events":    [{"name": "signup", "count": 12, "visitors": 11}]}
```

- `period`: `today` is the current UTC day with `bucket: "hour"`; `7d`/`30d` are the last N UTC days including today with `bucket: "day"`; `custom` takes `from`/`to` (inclusive days), `bucket` is `hour` when from = to, else `day`. `to` is exclusive in SQL (`< to + 1 day`).
- `pages`, `referrers`, `browsers`, `os`, `devices` are the top 10 by visitors, then pageviews, then name. Lists exclude nulls. `events` excludes `pageview` and is the top 10 by `count` (rows with that name), then `visitors`, then name; the UI renders its two numbers as "count" and "visitors".
- The timeseries is dense: every bucket in the period appears, zero-filled, generated with DuckDB `generate_series` and a left join.
- `visitors` is `count(distinct visitor)`; `pageviews` counts rows with `name = 'pageview'`. `views_per_visitor` is rounded to one decimal, 0 when there are no visitors.

### Tracker (`resources/public/p.js`)

Hand-written, no build step, under 2 KB unminified, served with a day of caching. Behaviour:

- Reads its own `<script>` tag (`document.currentScript`) for `data-hash` and `data-manual`, and derives the endpoint from its own `src` (`/p.js` → `/api/event`).
- Sends `{d: location.hostname, u: location.href, r: document.referrer, n: "pageview"}` on load, unless `data-manual` is set. `r` is sent only on the first hit of a page load; later route changes send `r: ""`.
- Wraps `history.pushState` and `history.replaceState`, listens to `popstate` (and `hashchange` when `data-hash` is set); fires a pageview when `location.pathname` (plus hash in hash mode) differs from the last sent one. In hash mode every payload also carries `h: location.hash`, which the server appends to the stored path; outside hash mode `h` is omitted and fragments are dropped.
- Skips sending when `location.hostname` is `localhost` or `127.0.0.1`, or the protocol is `file:`, unless `data-dev` is set (e2e uses it).
- `window.pagelet = function (name, props)`: sends `{d, u, r: "", n: name, p: props}`. Calls made before the script loads are queued on `window.pagelet.q` by the snippet pattern `window.pagelet=window.pagelet||function(){(window.pagelet.q=window.pagelet.q||[]).push(arguments)}` documented in the README; on load the script drains the queue.
- Transport: `navigator.sendBeacon(url, new Blob([json], {type: "text/plain"}))`, falling back to `fetch(url, {method: "POST", body: json, keepalive: true, headers: {"Content-Type": "text/plain"}})`.

### Auth

`ADMIN_PASSWORD` env var. Unset in development defaults to `admin` with a printed warning line at startup. The server stores `(hash/sha256 password)` once at config time and compares hashes. Sessions: `random-hex` ids in the `sessions` table, cookie `session=<id>; Path=/; HttpOnly; SameSite=Lax; Max-Age=31536000`, plus `Secure` when `x-forwarded-proto` is `https` (copy `session-cookie`/`parse-cookies` from `~/Projects/quickmeet/src/quickmeet/auth.lg`). Sessions older than 365 days are ignored.

### Error handling

- Ingest never returns an error to the browser: bad input is 400 only for unparsable JSON or a missing field; anything the server chooses to drop is still 202.
- API errors are JSON `{"error": "..."}` with 400/401/404/409. Unexpected exceptions become 500 with a logged stack, as in quickmeet's routes.
- The flush loop catches every exception per batch, prints it, and continues; it never dies.

### Testing strategy

- `lgx test` (let-go, `test/pagelet/`): pure functions (visitor hash, UA normalisation, event parsing, IP extraction), stats queries over an in-memory DuckDB seeded with known events, routes over a throwaway file (login, sites CRUD, event → flush → stats), and a system test on port 0 through real http including 50 concurrent `POST /api/event` all answering 202 and all counted after a flush.
- Playwright (`e2e/`): the tracker on a fake SPA served with `page.route` for `http://tracker.test/**`, asserting pageviews and a custom event appear in the stats API after the flush; and the dashboard (login, add site, open dashboard, see the numbers, online widget shows 1).
- CI (`.github/workflows/test.yml`): `lgx test`, `lgx ui-build`, `lgx e2e`, then build the Docker image and smoke-test it with curl, following `~/Projects/quickmeet/.github/workflows/deploy.yml`'s smoke step. CI needs gcc (present on ubuntu-latest) and caches `~/.lgx/runtimes`, `~/go/pkg/mod`, `~/.cache/go-build` keyed on `lgx.edn`. No `CGO_ENABLED=0` anywhere: the duckdb driver is cgo.

### Docker

`debian:trixie-slim` plus `ca-certificates` and `libstdc++6`, copying `bin/pagelet` built outside the image (as quickmeet does). Trixie, not bookworm: the binary built on ubuntu-latest links glibc 2.39 and bookworm ships 2.36. The image is dynamically linked and must not be tested with `file | grep static`.

### Known let-go/lgx constraints this design works around

- Handlers share one dynamic-binding stack → no `binding` on the request path, no HoneySQL.
- No response streaming → online-now is polled, not pushed.
- `signal-notify` is Linux-only → fallback to `http/wait`.
- `lgx build --target` cannot cross-compile cgo → native builds only; CI builds on Linux.
- Static resources are read as strings → Task 13's font check.

## Environment notes for the executor

- Tools come from mise: run `mise install` in `~/Projects/pagelet` after Task 1 writes `.mise.toml`. `go` and `node` are not on the bare `PATH` otherwise. A C compiler (`gcc`) must be on the machine; check `gcc --version`.

- `lgx build` runs top-level forms at compile time: keep every side effect inside `-main` behind `(when-not *compiling-aot* (-main))`.
- let-go namespaces used: `hash` (`hash/sha256` → lowercase hex string), `async` (`chan`, `timeout`, `alts!!`, `>!!`, `<!!`, `close!`), `go-loop` (core macro), `syscall` (`signal-notify`, `SIGINT`, `SIGTERM`), `json` (`read-json`, `write-json`), `http`, `io`, `os`, `string`. Look up exact signatures in `~/Projects/lgx/docs/knowledge-base/let-go-stdlib-quick-ref.md` and `~/Projects/let-go/pkg/rt/` before using one.
- The duckdb package's value rules: `count()` and `sum()` come back as ints, dates and timestamps as ISO strings, `round()` as a float. See `~/Projects/letgo-packages/duckdb/README.md`.
- Never run `git push`; the repo has no remote on purpose.
